# Runtime

The native runtime is written in C11 and built with CMake. It will host recompiled game
code next to an interpreter fallback and the PC Engine hardware (VDC, VCE, PSG, timer,
interrupt controller, CD-ROM, ADPCM) plus high-level replacements for the System Card
calls the game uses.

## Building

```sh
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER=clang
cmake --build build
ctest --test-dir build --output-on-failure
```

## CPU interpreter (`runtime/cpu/huc6280.c`)

One instruction per `hu_step()`, against a 21-bit physical bus through MPR0-7.
Returns CPU cycles; speed (CSL/CSH) is reported, not applied: converting to
master-clock time is the system's job.

### Conformance

Validated against [SingleStepTests/huc6280](https://github.com/SingleStepTests/huc6280)
(MIT, generated from Mesen; 2,500 tests per opcode). Put the v1 `*.json.bin` files in
`work/sst/v1`, or set `-DSST_DIR=...`.

Result: **253/256 opcodes pass every test; 639,592/640,000 tests overall (99.94%).**
Registers, flags, MPRs, all recorded RAM and total cycle counts are checked.

Behaviours the tests pinned down:

- ST0/ST1/ST2 take 4 cycles
- TSB/TRB set N and V from the operand before modification
- PLP/RTI never leave B set in P (T is restored from the stack)
- TMA with several mask bits returns the OR of the selected MPRs
- Block transfers push Y, A, X *before* fetching their six operand bytes
- T-mode applies to ORA/AND/EOR/ADC (not SBC), +3 cycles; decimal ADC/SBC +1 cycle

Known differences: TII (73), TDD (C3) and TAI (F3), about 400 tests in total. In every case
a transfer of up to 64 KiB wraps around the address space and overwrites its own
source or the stack mid-copy. The suite records only 500 RAM pairs and 500 bus
cycles, so the generator state needed to model these cases is not available.
Game code does not do this. The test harness also treats bytes copied from
unrecorded addresses as unknown, because the generator's background memory is random.

Not covered by the suite and still to do: interrupt timing (including the one-instruction
delay after CLI/SEI/PLP), VDC/VCE access wait states, and the timer and interrupt controller,
which belong to the system layer.

## System layer (`runtime/pce/`)

| File | Contents |
|---|---|
| `pce.c` | memory map (Super RAM `$68-$7F`, CD RAM `$80-$87`, BRAM `$F7`, WRAM `$F8-$FB`, I/O `$FF`), interrupt controller, timer, joypad, scanline-timed frame loop (263 lines × 1365 master clocks) |
| `video.c` | VCE palette; VDC registers, VRAM, VRAM/SATB DMA, raster/vblank interrupts, background + sprite scanline renderer |
| `disc.c` | CUE + ISO/BIN/WAV reader, or a `.chd` through `chd.c`, addressed by absolute LBA |
| `chd.c` | `.chd` images read in place: CHD v5, the `cdlz` / `cdzl` / `cdfl` codecs (docs/distribution.md, CHD) |
| `bios_hle.c` | System Card functions in C, run when the CPU reaches a jump-table address |

Bank `$00` holds a small ROM of our own: the interrupt stubs follow the System Card's dispatch
rule (bit set in `irq_m` → jump through the work-RAM vector), plus the two bank-number bytes
the boot code reads. No System Card image is needed.

System Card functions implemented: CD_BASE, CD_READ (all modes), CD_STAT, CD_PLAY, CD_SEARCH,
CD_PAUSE, CD_FADE, AD_TRANS, EX_GETVER, EX_SETVEC, EX_JOYSNS, EX_SCRMOD, EX_SCRSIZ, EX_DOTMOD,
EX_MEMOPEN, MA_MUL8U/8S/16U, MA_DIV16U/16S.
BM_FORMAT/FREE/READ/WRITE/DELETE/FILES: backup RAM in the System Card's file format (`bram.c`),
saved by the frontend in the user's pref folder.
AD_PLAY/STOP/STAT/READ/WRITE/RESET drive the ADPCM player in `sound.c`.
AD_CPLAY streams ADPCM straight from the CD. Stubbed (return success): EX_SATCLR.
EX_GETFNT (font glyphs for a Shift-JIS code; 16x16, or 12x12 in the top-left of the same
32-byte, 16-row layout, as the System Card returns them; A = 1 for codes outside its JIS rows
0x21-0x27 and 0x30-0x4F) draws from `kanji_font.c`, Shinonome Gothic 12/16 (public domain),
generated by `tools/fonts/make_kanji_font.py`, since players supply no System Card. The
Japanese disc draws its attract-mode story with it (12x12), the English translation one word.

## Sound (`runtime/pce/sound.c`)

- **PSG** (sound effects, and the chip music: the pre-boss and boss rooms, the stage clear,
  death, game over and all clear jingles): 6 wavetable channels (32 x 5-bit samples), DDA mode,
  noise on channels 4 and 5, 5-bit volume in 1.5 dB steps and 4-bit channel/global balance in
  3 dB steps. LFO: channel 1's waveform, clocked `lfo_freq` times slower, modulates channel 0's
  period (x1, x16, x256) and is not heard itself (the game never turns it on).
- **Band-limited tones.** A tone channel is a stepped wave, which the hardware's analog output
  filters: only the note's harmonics are heard. Up to 1.2 each output sample took the step
  under it at 44.1 kHz, which folded everything above 22 kHz back as tones that are not the
  note's: 11-27 dB under the notes on the game's waveforms, which made the chip music sound
  sour and out of tune (issue #8; its pitch, tempo and waveforms were right). Each output
  sample is now the stepped wave through a windowed sinc (cutoff 20 kHz, Kaiser beta 8, 24
  output samples: flat to 15 kHz, -1 dB at 18 kHz, -80 dB from 26 kHz), worked out from the
  channel's phase and period alone, so the Sound struct and save states are unchanged. What is
  left off the note's harmonics up to 16 kHz is 78-81 dB under them, the 16-bit output's own
  floor (`sound_test` checks it is under -60 dB). Tones above 4.1 kHz (period under 27, sound
  effects only) are averaged over their output sample instead, to bound the cost: about
  0.1-0.15 ms a frame for six channels of music, 0.4 ms at most. The tone channels come out
  0.27 ms late; noise and DDA are as before.
- **ADPCM** (voices): OKI MSM5205-style 4-bit ADPCM from the 64 KiB ADPCM RAM at
  32 kHz / (16 - rate), **each byte's high nibble first**, as the hardware plays them (MAME's
  PC Engine CD does the same). Low nibble first (before 0.11.1) turned the voices into a slow
  random walk that kept hitting the 12-bit limits: Death's first line clipped 92 times and had
  almost all its energy below 80 Hz; high first it never clips and has speech's spectrum and
  pitch. Linearly interpolated to 44.1 kHz; mixed at 12-bit full scale = 16-bit full scale,
  half the CD audio's level (MAME's 0.5 against 1.0). AD_STAT reports busy while a clip
  plays; the game waits on that, so it affects game timing.
- PSG writes and ADPCM starts are time-stamped with the master clock: the sound module renders
  up to that moment before applying them. CD audio is mixed in at output (`pce_audio_render`).
- A frame of the emulation runs about 0.4% over the nominal 263 x 1365 master cycles (a line
  ends after the instruction that crosses it; `rondo_headless` prints the average), so it
  makes about 740 samples of PSG + ADPCM where the output takes 737. Before 0.11.1 the rest
  waited in the buffer: sound effects and voices fell behind the picture and the CD music
  until, after about 90 s, they were 0.37 s late and samples were dropped every frame.
  `sound_take_fit` now fits each frame's sound to the frame's output (pitch 0.4% up), so
  nothing waits; a backlog (frames run without output, e.g. a test) is dropped.
- `rondo_headless --wav FILE [--mute-cd]` records the output; the summary reports PSG writes and
  how long PSG and ADPCM were audible.

CD audio: CD_PLAY/CD_SEARCH positions are BCD MSF (`$40`), LBA (`$00`) or track number (`$80`);
the low bits of the end-type byte select repeat (1) or play once. `pce_audio_render()` streams the
WAV/BIN audio tracks at 44.1 kHz with fades.

## Save states and rewind (`runtime/pce/state.c`)

- A snapshot is the whole emulated machine (`Pce`) with host-side fields zeroed: disc handles,
  memory-map pointers, framebuffer, audio output queue, diagnostics, input. Restoring keeps the
  live host fields and invalidates the recompiler's cached code checks (they are keyed by the
  per-bank write counters a restore rolls back).
- Save-state files: header (format, state size, disc fingerprint) + the snapshot, delta-coded
  against zeros (about 380 KB). States from another disc or another build are refused.
- Rewind: after each frame, the XOR difference to the previous snapshot is stored as zero-run /
  literal-run tokens (about 0.8 KB per frame) with that frame's input. XOR is its own inverse, so
  applying the newest difference steps the snapshot back exactly one frame. While rewinding, the
  frontend restores each earlier state and replays one frame of it to show the picture, with
  audio muted; on release play continues from the exact rewound state.
- `build/state_test <game.cue>`: restore + replay and state files reproduce the machine state
  byte for byte; rewinding N frames lands exactly on the recorded state.
- `rondo.exe --autotest` saves, loads and rewinds by itself and logs the result to rondo.log.

## Windowed frontend (`tools/frontend`, needs SDL3)

```sh
build/rondo.exe "<path>/game.cue"
```

| Action | Gamepad | Keyboard | Sends the game |
|---|---|---|---|
| Move | d-pad / left stick | arrows (and keys of the player's own) | d-pad |
| Jump | A (South) | X | I |
| Attack | X (West) | Z | II |
| Sub-weapon | B (East) | C | Up + II (macro) |
| Item Crash | Y (North) | V | SELECT |
| Backflip | RB | A | I, release, I (macro) |
| Run (hold) | LB | S | (frontend: speeds the walk up, `game_apply_run`) |
| Pause | Start | Enter | RUN |
| Menu | Back | F1 / Esc | (frontend) |
| Rewind (hold) | LT | R | (frontend) |
| Save / load state, slot | | F5 / F8, F6 / F7 | (frontend) |
| Fullscreen | | F11 | (frontend) |

Macros: the game ignores presses shorter than 3 frames, so each macro step lasts 4 frames;
the backflip is the second I press while still rising (2-8 frames after the first press
ends works, 14 is too late; measured with `rondo_headless --press`).

Controls (`binds.c`): the actions the player can rebind (Jump, Attack, Sub-weapon, Item Crash,
Backflip, Run, Pause, Menu, Rewind, Save state, Load state, and Move up / down / left / right:
`keys_only`, a key of the player's own in addition to the arrows, none by default, so WASD
can move; `bind_assign` refuses them a controller button), each with a controller button
(SDL gamepad button, the triggers as `BIND_LT` / `BIND_RT`, or a combination of two,
`BIND_COMBO(hold, press)`: Back + RB) and a key (scancode), kept in
`Settings.bind_pad` / `bind_key` and settings.ini (`bind_pad_jump = 0` ...). `bind_assign`
swaps with the action that had the control, leaves an action given its own control as it
was, and refuses moving controls, Esc, F6 / F7 and F11; `bind_clear` (X / Delete on a row:
`NAV_CLEAR_PAD` / `NAV_CLEAR_KEY`) leaves an action without one where the game can do without
it. `input.c` reads every
action through them (`input_held`, `input_pressed`; a trigger is pressed past half way and
let go below a quarter); moving and the menus' own navigation stay fixed. A combination is
pressed when its second button goes down while the first is held; that second button is then
"swallowed" (not its own action) until let go, and a button that starts any combination gives
its own press-type action (Menu, Save / Load state) on release, only if no combination used it
(`Input.armed`; opening or closing the menu forgets it). Held actions on such a button (game
buttons, run, rewind) still start at once. On the Controls page choosing a row counts down
from 5 (`menu_capture` follows what is held, in the order pressed; `menu_update` ends the
count): the buttons held at the end become the control (two: a combination, the first pressed
held first; three or more are refused), else a key held, else whatever was last pressed
together. Esc or a click leaves it. The features test checks the rules (`bind_check`), drives
an SDL virtual controller through Back + RB / Back + LB, Back alone and the shared RB / LB
(`input_check`), and feeds the count held buttons, a tap, a key, three buttons and nothing,
with photographs of it counting.

Modules: `input.c` (mapping, macros, menu navigation), `menu.c` (pages, persisted to
`settings.ini` by `settings.c`), `video.c` (placement and filtering), `game.c` (what the
frontend knows about the game: main state, cheats, run), `prompt.c` (the title's prompt) and
`wide.c` (16:9 widescreen, below); the last three are also linked into `rondo_headless`.

Video: aspect 4:3 / square pixels / stretch, fit or whole multiples, filters Sharp (nearest
upscale to a whole factor into a render target, then linear to the final size), Nearest and
Smooth. On wide screens the sides show the picture blurred (downscaled to 16x14, scaled up
linearly, dimmed). The window is high-DPI aware, so fullscreen renders at the display's
native resolution (e.g. 3840x2160). Frames are paced at 59.83 Hz by the frame timer
(`rondo.log` counts frames that came over 1.5 frame times after the last, `frames late`,
for telling the game's pacing from a recorder's). VSync
(on by default; `set_vsync`, `SDL_SetRenderVSync` 1, adaptive if that is refused) shows each
on the screen's refresh, so it never tears; the timer still sets the pace, so on a 60 Hz
screen about one frame in 350 is shown twice. Test runs turn it off to run uncapped.
`rondo.log` records the renderer and whether VSync is on.

16:9 widescreen (`wide.c`; Video > Widescreen, off by default, off in hardcore mode). The VDC
draws `vdc.wide` extra columns each side of a 256-pixel picture from the background map and
sprite table (`fb_wide` latched per frame; the original 256 start at `fb[fb_wide]`; the 16
sprites a line limit is lifted in a widened picture; columns beyond the room's walls, or
clipped rows, are black behind the sprites). The extension fills the window's shape
(`wide_extent`: 42 a side for 16:9 at 4:3 TV pixels, 70 with square pixels but at most 64
(`WIDE_STREAMED`: the background is drawn (STREAM / 32) * 32 = 64 px past the 256 at all
times; at 70 its last 6 px showed what the map held before, every 32 px walked); rounded down
to even) up to `WIDE_MAX` = 72. The few pixels rounding leaves short of the window's shape
are taken up by widening the picture to fill it (`video.c`, `place`, under 5%, Fit screen
only). The game itself already prepares 64 px past each side: objects spawn and start
moving 64 px out, so at 42 they are left exactly as the game has them and play is
unchanged. Past 64 (square pixels) objects spawn and start moving 72 px out instead
(below). 0.6-0.12 went to 112 px for 21:9 and moved spawning, removal and screen-fixed
generators out to 128 px at every width, which made enemies come on earlier. The changes
are byte patches, each checked against the original bytes (the game loads code from the
disc as it goes):

- Background (put in or taken out as a room starts, `Pce.on_entry` at 6F:A94C / A9B1, only
  for rooms the camera scrolls sideways through): columns streamed 80 px out (enough for
  72; 96 or 112, as in 0.6-0.12, put other layers' blank column tops into the view of
  Stage 2-1's far-trees band, which is not streamed itself, as a black strip) (and drawn at
  the old 64 too, for scenery stage code first draws to 64 only), the room start drawing 16
  columns, rows streamed during vertical scrolling drawn across the whole 512-pixel map.
  Room starts take a few frames longer (Stage 1: 5 frames). While a column is drawn at the
  old distance the distance table holds the old value; a frame that ends right then (the
  game running long) still counts the change as in (`patches_in`; before, such a frame was
  shown 4:3, a bar flicking in and out every few seconds).
- Objects (put in or out with the background, in every widened scrolling room): spawning
  (69:1E68 / 1E7F) and starting to move (70:A0B0 / A0BD) at `object_reach` past the 4:3
  screen, the extension + 50 px (`OBJECT_MARGIN`: wide sprites drawn around their X, such as
  the broken bridge's sections, appeared inside the picture's edges at 72), at most 120:
  92 at 42 px a side, 120 at 70. Screen-fixed generators follow (`move_generators`). Removal
  stays at 128 px. A save state made in a widened room holds the changes with their bytes
  moved: taken as in, so they follow the frame's values from the first frame.
- Drawing (follows each frame's choice of wide or 4:3): the sprite builder (72:8000) lets
  pieces through out to `WIDE_MAX` px either side; objects the game parks just off the left of its
  256 pixels (the Prologue's horses) are not drawn, via a per-slot table at $FE80 in our
  bank $00.
- Echoes, for weather drawn as objects (Stage 2's rain: two objects of type 07, kind $C2,
  fixed to the screen, sweeping down and left from X 168 to 71 every 18 frames, each frame
  a spread of 13 drops about 128 px either side, so it only ever covers 256 pixels). Each
  object is drawn through $FC00 (72:803F), which, for a slot the ECHO_TABLE at $FCC0 marks,
  draws it again with its X 256 more and 256 less, while 16 sprite entries are left. The
  culling (72:8123 through $FC40) tells the copies apart by $8066's return address on the
  stack and keeps their pieces only past the 256 pixels on their own side, so the rain tiles
  across the wider picture and the original 256 pixels show what they did (but for a drop
  crossing the left edge). The host marks objects fixed to the screen, not the HUD, on it
  and moving (a banner or a generator does not). Checked over 600 frames of the rain:
  game RAM unchanged, interpreter and recompiled pictures identical.
- The HUD (slots $57, $56) is moved to the left edge of the widened picture (from anywhere
  widescreen could have put it, so a save state from another session is put right). Its
  sprites are built during a frame and shown with the next, whose picture is shifted for the
  camera as this frame leaves it, so with Level ends it is put again as the sprite building
  starts (72:8000, through `Pce.on_entry`), the camera moved by then: put before the frame it
  was a step behind and jittered by a pixel as the camera stepped 1 and 2 px. A boss's
  health bar (slot $55, type 5, sliding in from X 254 to 216) cannot be moved as an object
  (past 253 its own code slides it in again), so its sprites (patterns $1F8-$1FF) are drawn
  at the picture's right edge instead (`vdc_set_sprite_move`).
- Edge spawns: some rooms send enemies in from fixed places just past the screen's edges,
  whatever the camera does (Stage 2's castle hall: ghouls, kind $29, at X -24 / 280, and
  kind $31 at 272), which would put them inside the wider picture. On the frame such an
  object is first drawn at -16 / -24 / -32 or 272 / 280 / 288 (not fixed to the screen, not
  the HUD; things thrown from off screen come out where the thrower is), it moves out by the
  picture's extra width on that side, keeping its distance from the edge, at most 80 px past
  the screen (`EDGE_SPAWN_MAX`: kind $31 removes itself from 86 px out).
- Scenery moved round: Stage 2's bridge pillars are three objects (kind $44, 128 px apart)
  the game moves 384 px to the other side once one passes X -32 or 287, out of the 4:3
  picture but inside the wider one. Objects of a kind seen jumping by 376-392 px, or a row
  (every object of a kind, three or four, exactly 128 px apart: not a splash's particles,
  three of which can line up by chance and, echoed, slowed the bridge boss), are echoed like the rain (drawn again 256 px
  either side, the copies kept only past the 256 pixels on their own side), which puts a
  copy where the next pillar round would be. The game moves a pillar 383 px, not 384, so
  each row is kept exactly 128 px apart (a pillar a pixel or two out of step is put back:
  else a copy lands a pixel off the pillar it meets). No copies onto a pillar the game is
  hiding (frame 0), and none that would be seen within 96 px of a room's end wall: the
  bridge ends in a pier where the next pillar would be, and the game, moving its pillars
  only out of the 4:3 picture's sight, never shows one there. Forgotten as each room starts.
- Scenery bands drawn only as far as the 4:3 picture shows them (Stage 2's bridge: the
  distant hills, castle and trees, blank tiles over 16 of the map's 64 columns): each map
  row seen scrolled apart from the playfield in the room (a row a playfield line shows in
  the same frame excepted) has its longest blank stretch, if 12 tiles or more, filled from
  both ends with the tile most often after (before) the one at its end in the band's rows
  (`scenery_fill`), drawn beside the original 256 pixels only (`vdc_set_map_fill`, by map
  position, so it scrolls with the band). Gaps between clouds are shorter and left alone; a row less than half drawn
  is no band (Stage 2's first room: an empty bottom row but for a tower, once seen scrolled
  apart, was filled with floor tiles).
- The room's walls are measured directly from the camera while it is within the room's
  limits (`room_walls`): the boat ride's room is 3584 px wide, more than the 2048 a wrapped
  12-bit distance covers, and its left wall came out on the screen's right (the background all
  black). Only the rain (kind $C2, type 7) is echoed as weather: the boat ride's boat and
  ferryman, fixed to the screen and bobbing, were drawn again 256 px over.
- Level ends follow the camera the game built its sprites with (`hud_at_build`, recorded and
  used by the next `wide_frame`): the game draws the playfield with that same camera, which is
  the camera before or after `wide_frame`'s point depending on how long its frames run (a slow
  frame, as on Stage 2's bridge, moves the camera while the next picture is drawn; on the
  stairs below it the game is done in time). Worked out from the camera at `wide_frame`, the
  picture and HUD shook by the camera's step at a room's end.
- Level ends (Video > Level ends, on by default; `Wide.edges`): within the extension of a
  scrolling room's left or right limit the picture is shifted (`vdc_set_wide_shift`,
  host-side, latched per frame like `fb_wide`; the original 256 then start at
  `fb[fb_wide - shift]`) so all the extra width is on the room's side and nothing past its
  wall shows; a room narrower than the picture is centred. A few patch bytes follow the
  shift each frame (`Patch.var`, written by `update_vars`; compared as anything): the sprite
  builder's right and left bounds and the echo copies' right bound grow by the shift; spawning
  and starting to move on the open side go out to extension + shift + 8, at most 120 px
  (removal is at 128), screen-fixed generators following (`move_generators`, now any
  distance); objects keep the game's 64 (72 with square pixels) on the other side and
  anywhere away from a room's end. Because the object patches are mostly their varying
  byte, whether they are in is kept in a flag (`objects_on`), not read from memory; with
  Level ends on they go in at 42 too (at the game's 64 until a shift needs more). A room
  starting within the extension of its left end is first drawn from the camera instead of
  144 px left of it (the room start's offset byte $B0 for $20; at its right end $00, from
  176 px left), so with square pixels the 140 px on the open side are there from the first
  frame. Off, everything is as before (frames identical). `rondo_headless --wide-edges`
  turns it on and prints each change of the shift. The stage title letters (slots $54-$55)
  stay centred on the game's 256 pixels, so they sit left of centre while the picture is
  shifted at a level's start.
- Wide menus (Video > Wide menus, on by default; `Wide.menus`), states $03 / $04 (title,
  file select): the menus' map holds nothing of theirs past the 256 pixels (filler tile
  $110, or the other page), so the VDC draws side tiles there instead
  (`vdc_set_side_tiles`, host-side: 12 BAT words a map row each side, keyed by the map row
  and the column's distance from the first / last column the 256 pixels show; no sprites
  beside the 256 meanwhile). `menu_sides` works them out each frame from the last frame's
  map: one X scroll for every line (else not), the map rows shown (`vdc_row_map_y`), the
  pairs of neighbouring BAT words across the shown columns of those rows counted, and each
  row carried on from its edge word by the word most often after (before) it, seen at
  least twice. The file select's waves are tiles 144-147 and 148-149 joined in any order,
  so they carry on seamlessly; the title's clouds have no repeat and stay 4:3. Wide once
  97% of the side tiles fill for 8 frames in a row (`MENU_FRAMES`); then held with the last
  sides that filled for up to 60 frames that do not (`MENU_HOLD`: a page sliding over puts
  its frames at the edges), so it does not flick to 4:3. While the menu's scroll moves (a page sliding
  over: the map holds both pages side by side), the sides show the map's own entries wherever
  the picture has not wrapped round the map, and sprites beside the 256 pixels too
  (`vdc_set_side_real`), so the page coming in enters at the screen's edge and the one going
  out leaves at the other. `rondo_headless --wide-menus`.
- Title art (Video > Title art, on by default; `titleart.c`): the title's and the stage map's
  art has no repeat, so their sides come from art files, 396 x 228: the built-in
  title_sides.png and map_sides.png (`title_art_data.h`, compiled into the game), each
  replaced by a file of the same name in the profile folder, and any other `*_sides.png`
  there (up to 8 in all). They hold no picture of the game's: each side
  pixel (columns 0-69, 326-395 of rows 0-224) is a palette entry (R = low 8 bits, G bit 0 =
  bit 8; alpha 0 = none), drawn with what that entry held when the line beside it was drawn
  (`vdc_line_palette`, taken every 16 lines: the lightning changes colours while the picture is
  drawn), so the art follows the fades, the clouds' shimmer and the lightning as
  the game's pixels do; rows 225-227 hold 'R' 'S' '1' and the screen's 28 x 32 map entries
  (`titleart_layout`: each tile row's middle line's map row and first column). A frame is the
  screen when 85% of its map entries match (75% once shown: a prompt blinks, a stage name
  changes), which holds from its first frame (the map is set before the fade-in); while the
  middle is all black (its palette is up before its background is), the sides are black too.
  The screen's first column, a shade darker, is drawn as the next. The files are made by a
  converter from art generated around a template: `rondo_headless --dump-layout FRAME:FILE`
  writes the screen's map entries and each background pixel's palette entry for it, and
  each side colour (snapped to the screen's own) becomes the entry the screen's own edge uses
  it for, nearest row first (the same colour can be in two palettes, only one of which flashes).
  `rondo_headless --title-art FILE` (the file's pixels, raw ARGB) writes shots with it. The
  Setup SDK's source list (`tools/make_sdk.cmake`) has `titleart.c`.

A room is shown wide when the background changes are in and it scrolls sideways, or when it
is one screen wide but its scenery scrolls past (the carriage chase); bands of rows holding
something parked off-screen (the Prologue's carriage) are cut to 256 until it drives in. The
picture grows out to the sides over about half a second. Save states hold the patched code
(the four `Vdc` widescreen ints are cleared in the file, so states keep the 1.2 layout).
`rondo_headless --wide N` runs with N px a side, `--wide-skip LIST` leaves patches out,
`--wide-report FRAME` lists which are in. Checked on the USA disc (Prologue, Stage 1) with
the interpreter and the recompiled build. On the interpreter, with the drawing changes alone,
game RAM matches a 4:3 run frame for frame (only the sprite builder's zero-page and stack
scratch differ). On the recompiled build, drawing more sprite pieces in the CPU-heavy
carriage chase moves one of its slowdown frames. The features test runs with widescreen on
in its 16:9 window.

Screen effects (`video.c`, `draw_effect`; Off by default): passes of the ordinary renderer,
no shaders. The picture is drawn at its size on screen into a render target, softened
sideways for Composite (four shifted copies blended in turn), drawn again added at a fraction
to make up for the darkening, and multiplied (`SDL_BLENDMODE_MOD`) by a scanline profile: a
1-pixel-wide texture with the brightness of every screen row, 1 - depth * cos^4 across each
game line, averaged over 8 points per row so lines come out even at any scale. The target
then goes on the screen, flat or for Curved CRT on a 48 x 36 mesh bowed outward (x scaled by
1 - k y^2, y by 1 - k x^2), under an aperture grille (a 3 x 1 RGB texture tiled at the
screen's own pixels, doubled from 1600 rows, multiplied), a glow (the picture downscaled to
128 x 112 and 64 x 56, added) and a vignette. Geometry takes its alpha from the vertices, not
the texture's alpha mod, so the mesh passes put it there. Each effect is set to keep the
picture's average brightness within about 6% of the plain picture; each costs under 0.4 ms
a frame at 1080p. Effect strength scales them by 0.6 / 1 / 1.4. The features test takes a
screenshot of each.

Cinematic skip: story scenes run in main state `$0A` (RUN does not skip them in the game).
Skipping runs the emulation at full speed, silently, until the state changes (the 3,566-frame
Stage 0 scene takes under a second), then records one rewind step across the whole scene.

The logo and the intro use the game's own skip instead (bank `$6B`, the overlay at `$8000`):
the logo (state `$00`) ends early on a new RUN press when `$3F83` and `$3F84` are both set,
with `$37 = $FF`, which sends state `$02` to sub-state `$03` (the title screen's script)
past the intro; the intro (state `$02` sub-state `$01`) goes to the title on a new RUN press
when `$3F83` is set. The game sets `$3F84` at the end of the logo and `$3F83` at the end of
the intro (and in the logo's first step when the backup RAM check at `$40E7` returns 0), so
on a first power-on START does nothing until both have been shown. Unless Skip cinematics is
Never, the frontend sets both flags during the logo and intro (`game_allow_power_on_skip`),
and Start, Jump or Attack (or Play on the start screen, or Automatically) makes it press RUN
for the game every 8 frames where it looks (`game_power_on_skippable`) until the title screen
is up: about 0.3 s from power-on. The title screen is silent either way; the game starts its
attract sequence about 14 s later.

Cheats (`game.c`): health losses are undone while playing (state `$05`) and hearts are kept at
99 while playing, unless either drops more than 12 times a second: that is the stage's end
counting health, then hearts, into the score a step a frame (docs/findings.md, "End of a
stage"), which only goes on once each is 0. That value is then left alone until 3 quiet
seconds pass or the state changes (`GameTally`). Lives losses are undone outside the menus.
`build/cheat_test` plays the stage's end and some hits and sub-weapon throws against them.
Maria unlocked sets bit 0 of `$1F40` (the current save record) while playing; Play as Maria
sets the character byte `$9F` to 1 whenever a stage may be loading (outside gameplay and
while a stage sets up), so every stage loads Maria's code, the Prologue included.

Run (`game_apply_run`): Rondo sets the player's X velocity once when a walk starts (±$0140
for Richter, ±$0160 for Maria; Richter's jumps ±$0150). While the run button is held, those
exact values in the facing direction are scaled by 2.3 / 1.25 (SotN's run against its walk,
which equals Rondo's), and the walk animation's frame timer gets an extra step on 5 frames
of 6. The game's own movement code then handles walls, stairs and the camera.

Super Castlevania IV moves (`moves.c`, Gameplay page, off by default and in hardcore mode;
the ideas from Pizzano's Super Rondo of Blood hack, none of its code): with "8-way whip and
doves" Attack aims where the d-pad points (up, up and ahead; in the air also down and down
and ahead); with "Limp whip" Attack kept held after a whip hangs it from Richter's hand.
Up + II is the game's sub-weapon throw, so while Attack is held the game is not given Up
(`moves_pad`; the Sub-weapon control's own Up + II still throws), and while the whip hangs
it is given no direction at all (on the attack's last frame the game takes one as the end
of the attack). The game itself stays as it is; around each frame (docs/findings.md, "The
whip"):

- The whip's direction is the d-pad's while it winds up (whip frames before 05), kept
  through the strike (05-07). For each frame of a turned strike the strike's three box
  entries in Richter's code (`$6E:DDE8`, picked by `$DD56`) are rewritten before the frame
  and put back after it, so the game's own `$DD1F` gives the whip a box turned around
  Richter's hand (cut down by a fifth on the diagonals), and no save state or rewind step
  keeps them. Crouching and stair whips stay ahead.
- The strike's sprites (patterns `$1A0`-`$1AF` near Richter; palette 1, flashing through 3
  and 4) are left out of that frame's picture (`vdc_set_sprite_hide`, as `prompt.c` does)
  and drawn into it turned around the hand, from their own pixels in VRAM (each picture pixel
  takes the source pixel it turns back to).
- The limp whip holds Richter's and the whip's animation timers (`$0F90`) at 4 while
  Attack is held on the strike's last frame, as a state of standing or jumping attack; it
  is 8 links of 6 pixels (the last a 10-pixel tip) cut from the straight whip, the first
  turning toward the d-pad by 0.22 rad a frame (hanging straight down with none) and each
  next following the one before at 45% a frame. Its box (half 8 x 8) is on the tip.
  Letting go sets both timers to 1: the attack ends on the next frame, as it would have.
- A dove of Maria's flying out (its state 0) gets, after each frame, what its velocity
  turned to the aimed direction adds to its position; the game slows it and brings it back
  as usual.

While rewinding nothing of this runs (the frames are shown as the game drew them). The
features test (`--autotest-features`) turns both on in Stage 1: an upward whip, then the
whip held limp and swung ahead, logged (`features: moves: ...`) and photographed
(`moves_up.bmp`, `moves_limp_hanging.bmp`, `moves_limp_ahead.bmp`). `rondo_headless --moves
eight,limp` plays them with the pad's II as Attack.

The title screen's prompt (`prompt.c`): the game's "PUSH RUN BUTTON!" (six sprites in
palette 7 at Y 136, the same on both discs) reads "PUSH START BUTTON!" with a controller
and "PUSH ENTER KEY!" on the keyboard (`input_pad_last`: the kind of device pressed last; a
controller if one is connected and nothing has been pressed yet). Before each frame of state
`$02`, if the six sprites are in the sprite table, they are left out of that frame's picture
(`vdc_set_sprite_hide`, host side: they still count as drawn for the line limit and sprite
0's collision, so nothing the game can see changes); after it the new line is drawn into the
picture in the game's own letters, cut from those sprites' patterns in VRAM, with A, E, K
and Y drawn in the same style in `prompt.c`. Its colours come from the palette as it is, so
it fades with the title. No game graphics are kept in the source.

The Discord status (`discord.c`, Gameplay page "Discord status", on by default): a thread
talks to the Discord app on the same computer through its local IPC endpoint (the named
pipe `\\.\pipe\discord-ipc-N` on Windows, the Unix socket `discord-ipc-N` in
`$XDG_RUNTIME_DIR`, `$TMPDIR` or `/tmp`, with the Flatpak and Snap folders, on Linux) with
Discord's own framing: a handshake with the application id, then `SET_ACTIVITY`. Nothing
else goes out to the network, and without the app it looks again every 20 s. Each frame
`main.c` says what it shows: the start screen, the intro, the title screen, the file menu,
a story scene, or in play the stage (`game_stage`, from `$81`: docs/findings.md, "Stages")
and "Playing as Richter / Maria" ("Paused" while the menu is open). A change goes out at
most every 5 s (Discord takes 5 in 20 s); the elapsed time counts from the game's start.
Turning it off clears it at once; closing the game clears it too. Test runs never start it.
The picture is the application's Rich Presence art asset `icon`; `RONDO_DISCORD_APP_ID`
names another application. `rondo.log` ends with how it went (`discord: shown on Discord
(last: Stage 5 | Playing as Maria)`, `the Discord app isn't running on this computer`, ...).

Start screen (`menu.c` page `PAGE_START`, the in-game menu's root swapped for one with Play
at the top; the option pages return to whichever root opened them): shown when rondo.exe
starts unless `--play` or the Start screen option is off. The game is loaded but does not
run behind it (no picture, no sound); Play starts it from power-on and goes straight to the

The look (`theme.c`; laid out after the Metroid: Other M port's menus, gothic, by candlelight
and moonlight, red kept to small rubies): panels are dark umber frames with a pointed-arch
top letting in pale moonlight, warmer toward the bottom, a gold border and inner line,
pinnacles at the arch's feet and a cross on its apex; dividers carry diamonds and a cross;
the selected row is a bar of candlelight with a gold cross for a cursor; notices are plaques
with pointed ends. The emblem is a rose window of blue and indigo glass lit by a candle
behind it. The start screen is a town at night: a deep blue sky, a pale moon high on the
left whose beams slant down onto the town, thin clouds and bats; a castle on a hill and the
town's rear rows in a cool mist; the town's warm glow; then the near row of houses (moonlit
roof edges, chimneys), a church with a lit belfry and street lanterns, the windows lit by
candles that flicker. Lights are added (`SDL_BLENDMODE_ADD`) as soft radial glows. The

Windows fit the screen (`fit.h`, shared with Setup): the game's opens at 960 x 720, or

Setup's window is 640 x 400 units, or 640 x 480 for a 4:3 screen (chosen by its "4:3

the screen's shape, under 1.4:1), up to twice that size, smaller to fit, and full screen

SDL's debug font, stand in if one cannot be read.
Skip cinematics (START, or automatic) runs the story scenes (state `$0A`) fast; the logo and
the power-on intro (state `$02`, sub-states `$00`-`$01`: the narration and animated opening,

Test modes: `rondo.exe --autotest` (save, load, rewind), `rondo.exe --autotest-features

Showcase (`showcase.c`): `rondo.exe --showcase SCRIPT` plays a scripted tour in real time with
sound, for recording a video of the game (OBS capturing the window). The script presses and
lets go of keys at set frames of the window (`wait N`, `press KEY...`, `release KEY...`,
`tap KEY... [N]`, `mark TEXT`, `shot FILE`, `quit`; SDL key names). They reach the game as a
player's keys would: as `TEST_INPUT` events, and in place of SDL's keyboard state
(`input_use_keys`). So menus, macros, run, rewind and save states all work as for a player,
and real input is ignored. The window is 1920 x 1080 pixels and cannot take the focus. The
options the script changes are saved next to it (`SCRIPT.settings.ini`), not in the profile.

script with its shots. The game's own timing is the same either way, but the menus' animations
follow the real clock.

Profile: settings, saves, states and the remembered disc live in the pref folder
(`%APPDATA%\RondoRecomp\RondoRecomp`), or in the folder named by the `RONDORECOMP_PROFILE`
environment variable (`locate_profile_dir`), which Setup and rondo.exe started from each
other inherit: a whole separate player, e.g. to go through the first run again. Without that

folder (on Linux's AppImage, `user` next to the AppImage file, from `RONDO_APPIMAGE`, since

renamed `user.old` (`user.old2` ...). The pref folder is worked out from `%APPDATA%` (on

RetroAchievements (`achievements.c`, `http.c`; game 4855): RetroAchievements' client library,
rcheevos 12.5.0 (`third_party/rcheevos`, MIT; built with `RC_NO_THREADS` and only the CD hashing,
`tools/rcheevos_sources.cmake`), runs the achievements, leaderboards and rich presence.
- The disc is identified by RetroAchievements' PC Engine CD hash: MD5 of the 22-byte title at
  sector 1 + 106 of the first data track, then the boot program's sectors. The library's own
  code hashes it, reading through the runtime's disc reader (`Disc`, every image format the game
  takes). The English patch keeps the original's boot sector, so both discs hash to
  `dc5a0e432c9e8a9ab9f514b729b574f3` = game 4855.
- Memory as RetroAchievements maps a PC Engine CD:
  - `$000000` work RAM
  - `$002000` CD RAM
  - `$012000` Super System Card RAM
  - `$042000` backup RAM (2 KiB)

  These are `Pce.wram`, `cdram`, `superram` and `bram` in that order.
- The library is checked after every emulated frame, story scenes run fast included, but not
  while rewinding.
- Server requests run on a thread each, with WinHTTP on Windows and on Linux the system's
  libcurl, loaded at run time (`libcurl.so.4`, then the GnuTLS build). Their answers are
  handed to the library on the main thread (`http_poll`), so it needs no locking. The
  User-Agent is `RondoRecomp/<version> (<system>) rcheevos/<version>`.
- The account: a password login answers with a token, and only the token is kept
  (`settings.ini` `ra_user`, `ra_token`). Later starts log in with it, and a rejected token is
  dropped.
- Save states keep the achievements' progress (hit counts) in `slotN.state.ra` next to the
  state. A state without one resets them.
- Hardcore mode turns off state loading, rewind, the cheats and the run; the library asks for
  a restart when it is switched on (`RC_CLIENT_EVENT_RESET`).
- Whether hardcore counts is the server's call, by the User-Agent's first word. RondoRecomp is
  not a client it knows yet, so it puts a notice at the top of the set: an achievement of its
  own (id 101000001, 0 points, unlocking 5 s in, never sent back), "Warning: Unknown Emulator",
  "Hardcore unlocks cannot be earned using this emulator." It then records hardcore unlocks
  as softcore and keeps no leaderboard entries. The notice is shown as a RetroAchievements
  pop-up, not an unlock. When its text says hardcore cannot be earned, the library runs
  softcore for that game (so the counts and the unlocks are the server's), the pop-up and the
  menu say "softcore only", and hardcore's rules stay on as set (switching it on still
  restarts the game, `ach_take_reset`, as RetroAchievements requires). Each load asks again, so a
  client the server registers later gets hardcore with no change here.
- `rondo --test-achievements` hashes each installed disc, asks the server which game it is (no
  login needed), and exits 0 when both are game 4855.
- The features test registers an achievement of its own on the game's state (`$30` = 05, `$31`
  = 01) through the same memory map. It must fire at the first frame of play after the
  opening cinematic (16105), in that state.

### Hardware behaviour this depends on

- **VDC status flags are only latched when their interrupt is enabled.** Rondo's vblank
  handler checks the raster flag first and takes a raster-only path when it is set. If a raster
  match is latched while raster interrupts are disabled, it arrives together with vblank and the
  frame logic never runs again (the game froze on the logo before this was fixed).
- **The raster counter keeps counting below the picture, and the raster interrupt on the
  first line after it comes before vblank.** The counter is `$40` on the picture's first line
  and counts every line until the next picture starts, so a compare of `$40` + the picture's
  height matches the first line of vertical blank. Rondo's water areas (the Stage 1 ferry)
  use that: a raster split at the water line (69:47E2, effect 8 of the table at 69:44E9)
  saves sprite palette 0 (Richter's) and fills it with blue for his reflection, and sets
  RCR `$121` (picture height 225), whose interrupt restores it (69:477D). The handler reads
  the status once and handles one cause, so vblank (`vdc_vblank`, with the SATB DMA) is
  raised half a line later than the compare (`pce_run_frame`). Before this, compares stopped
  at the picture's end: the restore never ran, the next frame saved the blue palette, and
  Richter stayed a blue silhouette for the rest of the area.
- Rondo never uses the timer: its timer handler is a bare `RTI`. The System Card leaves the
  timer stopped after reset (checked by running the original reset code with `--bios-reset`).
- Input arrives through the System Card's `EX_JOYSNS` variables (`$2228` held, `$222D` newly
  pressed, `$2232` previous), which the game refreshes every frame.
