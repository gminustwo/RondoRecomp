# Runtime

The native runtime is written in C11 and built with CMake. It will host recompiled game
code next to an interpreter fallback and the PC Engine hardware (VDC, VCE, PSG, timer,
interrupt controller, CD-ROM, ADPCM) plus high-level replacements for the System Card
calls the game uses.

## Building

```sh
cmake -S . -B build -G Ninja -DCMAKE_C_COMPILER=clang
cmake --build build
ctest --test-dir build --output-on-failure
```

## CPU interpreter (`runtime/cpu/huc6280.c`)

One instruction per `hu_step()`, against a 21-bit physical bus through MPR0-7.
Returns CPU cycles; speed (CSL/CSH) is reported, not applied: converting to
master-clock time is the system's job.

### Conformance

Validated against [SingleStepTests/huc6280](https://github.com/SingleStepTests/huc6280)
(MIT, generated from Mesen; 2,500 tests per opcode). Put the v1 `*.json.bin` files in
`work/sst/v1`, or set `-DSST_DIR=...`.

Result: **253/256 opcodes pass every test; 639,592/640,000 tests overall (99.94%).**
Registers, flags, MPRs, all recorded RAM and total cycle counts are checked.

Behaviours the tests pinned down:

- ST0/ST1/ST2 take 4 cycles
- TSB/TRB set N and V from the operand before modification
- PLP/RTI never leave B set in P (T is restored from the stack)
- TMA with several mask bits returns the OR of the selected MPRs
- Block transfers push Y, A, X *before* fetching their six operand bytes
- T-mode applies to ORA/AND/EOR/ADC (not SBC), +3 cycles; decimal ADC/SBC +1 cycle

Known differences: TII (73), TDD (C3) and TAI (F3), about 400 tests in total. In every case
a transfer of up to 64 KiB wraps around the address space and overwrites its own
source or the stack mid-copy. The suite records only 500 RAM pairs and 500 bus
cycles, so the generator state needed to model these cases is not available.
Game code does not do this. The test harness also treats bytes copied from
unrecorded addresses as unknown, because the generator's background memory is random.

Not covered by the suite and still to do: interrupt timing (including the one-instruction
delay after CLI/SEI/PLP), VDC/VCE access wait states, and the timer and interrupt controller,
which belong to the system layer.

## System layer (`runtime/pce/`)

| File | Contents |
|---|---|
| `pce.c` | memory map (Super RAM `$68-$7F`, CD RAM `$80-$87`, BRAM `$F7`, WRAM `$F8-$FB`, I/O `$FF`), interrupt controller, timer, joypad, scanline-timed frame loop (263 lines × 1365 master clocks) |
| `video.c` | VCE palette; VDC registers, VRAM, VRAM/SATB DMA, raster/vblank interrupts, background + sprite scanline renderer |
| `disc.c` | CUE + ISO/BIN/WAV reader addressed by absolute LBA |
| `bios_hle.c` | System Card functions in C, run when the CPU reaches a jump-table address |

Bank `$00` holds a small ROM of our own: the interrupt stubs follow the System Card's dispatch
rule (bit set in `irq_m` → jump through the work-RAM vector), plus the two bank-number bytes
the boot code reads. No System Card image is needed.

System Card functions implemented: CD_BASE, CD_READ (all modes), CD_STAT, CD_PLAY, CD_SEARCH,
CD_PAUSE, CD_FADE, AD_TRANS, EX_GETVER, EX_SETVEC, EX_JOYSNS, EX_SCRMOD, EX_SCRSIZ, EX_DOTMOD,
EX_MEMOPEN, MA_MUL8U/8S/16U, MA_DIV16U/16S.
BM_FORMAT/FREE/READ/WRITE/DELETE/FILES: backup RAM in the System Card's file format (`bram.c`),
saved by the frontend in the user's pref folder.
AD_PLAY/STOP/STAT/READ/WRITE/RESET drive the ADPCM player in `sound.c`.
AD_CPLAY streams ADPCM straight from the CD. Stubbed (return success): EX_SATCLR.
EX_GETFNT (font glyphs for a Shift-JIS code; 16x16, or 12x12 in the top-left of the same
32-byte, 16-row layout, as the System Card returns them; A = 1 for codes outside its JIS rows
0x21-0x27 and 0x30-0x4F) draws from `kanji_font.c`, Shinonome Gothic 12/16 (public domain),
generated by `tools/fonts/make_kanji_font.py`, since players supply no System Card. The
Japanese disc draws its attract-mode story with it (12x12), the English translation one word.

## Sound (`runtime/pce/sound.c`)

- **PSG** (sound effects): 6 wavetable channels (32 x 5-bit samples), DDA mode, noise on
  channels 4 and 5, 5-bit volume in 1.5 dB steps and 4-bit channel/global balance in 3 dB steps.
  LFO: channel 1's waveform, clocked `lfo_freq` times slower, modulates channel 0's period
  (x1, x16, x256) and is not heard itself.
- **ADPCM** (voices): OKI MSM5205-style 4-bit ADPCM from the 64 KiB ADPCM RAM at
  32 kHz / (16 - rate), **each byte's high nibble first**, as the hardware plays them (MAME's
  PC Engine CD does the same). Low nibble first (before 0.11.1) turned the voices into a slow
  random walk that kept hitting the 12-bit limits: Death's first line clipped 92 times and had
  almost all its energy below 80 Hz; high first it never clips and has speech's spectrum and
  pitch. Linearly interpolated to 44.1 kHz; mixed at 12-bit full scale = 16-bit full scale,
  half the CD audio's level (MAME's 0.5 against 1.0). AD_STAT reports busy while a clip
  plays; the game waits on that, so it affects game timing.
- PSG writes and ADPCM starts are time-stamped with the master clock: the sound module renders
  up to that moment before applying them. CD audio is mixed in at output (`pce_audio_render`).
- A frame of the emulation runs about 0.4% over the nominal 263 x 1365 master cycles (a line
  ends after the instruction that crosses it; `rondo_headless` prints the average), so it
  makes about 740 samples of PSG + ADPCM where the output takes 737. Before 0.11.1 the rest
  waited in the buffer: sound effects and voices fell behind the picture and the CD music
  until, after about 90 s, they were 0.37 s late and samples were dropped every frame.
  `sound_take_fit` now fits each frame's sound to the frame's output (pitch 0.4% up), so
  nothing waits; a backlog (frames run without output, e.g. a test) is dropped.
- `rondo_headless --wav FILE [--mute-cd]` records the output; the summary reports PSG writes and
  how long PSG and ADPCM were audible.

CD audio: CD_PLAY/CD_SEARCH positions are BCD MSF (`$40`), LBA (`$00`) or track number (`$80`);
the low bits of the end-type byte select repeat (1) or play once. `pce_audio_render()` streams the
WAV/BIN audio tracks at 44.1 kHz with fades.

## Save states and rewind (`runtime/pce/state.c`)

- A snapshot is the whole emulated machine (`Pce`) with host-side fields zeroed: disc handles,
  memory-map pointers, framebuffer, audio output queue, diagnostics, input. Restoring keeps the
  live host fields and invalidates the recompiler's cached code checks (they are keyed by the
  per-bank write counters a restore rolls back).
- Save-state files: header (format, state size, disc fingerprint) + the snapshot, delta-coded
  against zeros (about 380 KB). States from another disc or another build are refused.
- Rewind: after each frame, the XOR difference to the previous snapshot is stored as zero-run /
  literal-run tokens (about 0.8 KB per frame) with that frame's input. XOR is its own inverse, so
  applying the newest difference steps the snapshot back exactly one frame. While rewinding, the
  frontend restores each earlier state and replays one frame of it to show the picture, with
  audio muted; on release play continues from the exact rewound state.
- `build/state_test <game.cue>`: restore + replay and state files reproduce the machine state
  byte for byte; rewinding N frames lands exactly on the recorded state.
- `rondo.exe --autotest` saves, loads and rewinds by itself and logs the result to rondo.log.

## Windowed frontend (`tools/frontend`, needs SDL3)

```sh
build/rondo.exe "<path>/game.cue"
```

|---|---|---|---|
| Move | d-pad / left stick | arrows (and keys of the player's own) | d-pad |
| Jump | A (South) | X | I |
| Attack | X (West) | Z | II |
| Sub-weapon | B (East) | C | Up + II (macro) |
| Item Crash | Y (North) | V | SELECT |
| Backflip | RB | A | I, release, I (macro) |
| Run (hold) | LB | S | (frontend: speeds the walk up, `game_apply_run`) |
| Pause | Start | Enter | RUN |
| Menu | Back | F1 / Esc | (frontend) |

| Save / load state, slot | | F5 / F8, F6 / F7 | (frontend) |
| Fullscreen | | F11 | (frontend) |

Macros: the game ignores presses shorter than 3 frames, so each macro step lasts 4 frames;
the backflip is the second I press while still rising (2-8 frames after the first press
ends works, 14 is too late; measured with `rondo_headless --press`).

Controls (`binds.c`): the actions the player can rebind (Jump, Attack, Sub-weapon, Item Crash,
Backflip, Run, Pause, Menu, Rewind, Save state, Load state, and Move up / down / left / right:
`keys_only`, a key of the player's own in addition to the arrows, none by default, so WASD
can move; `bind_assign` refuses them a controller button), each with a controller button
(SDL gamepad button, the triggers as `BIND_LT` / `BIND_RT`, or a combination of two,
`BIND_COMBO(hold, press)`: Back + RB) and a key (scancode), kept in
`Settings.bind_pad` / `bind_key` and settings.ini (`bind_pad_jump = 0` ...). `bind_assign`
swaps with the action that had the control, leaves an action given its own control as it
was, and refuses moving controls, Esc, F6 / F7 and F11; `bind_clear` (X / Delete on a row:
`NAV_CLEAR_PAD` / `NAV_CLEAR_KEY`) leaves an action without one where the game can do without
it. `input.c` reads every
action through them (`input_held`, `input_pressed`; a trigger is pressed past half way and
let go below a quarter); moving and the menus' own navigation stay fixed. A combination is
pressed when its second button goes down while the first is held; that second button is then
"swallowed" (not its own action) until let go, and a button that starts any combination gives
its own press-type action (Menu, Save / Load state) on release, only if no combination used it
(`Input.armed`; opening or closing the menu forgets it). Held actions on such a button (game
buttons, run, rewind) still start at once. On the Controls page choosing a row counts down
from 5 (`menu_capture` follows what is held, in the order pressed; `menu_update` ends the
count): the buttons held at the end become the control (two: a combination, the first pressed
held first; three or more are refused), else a key held, else whatever was last pressed
together. Esc or a click leaves it. The features test checks the rules (`bind_check`), drives
an SDL virtual controller through Back + RB / Back + LB, Back alone and the shared RB / LB
(`input_check`), and feeds the count held buttons, a tap, a key, three buttons and nothing,
with photographs of it counting.

Modules: `input.c` (mapping, macros, menu navigation), `menu.c` (pages, persisted to
`settings.ini` by `settings.c`), `video.c` (placement and filtering), `game.c` (what the
frontend knows about the game: main state, cheats, run) and `prompt.c` (the title's prompt);
the last two are also linked into `rondo_headless`.

Video: aspect 4:3 / square pixels / stretch, fit or whole multiples, filters Sharp (nearest
upscale to a whole factor into a render target, then linear to the final size), Nearest and
Smooth. On wide screens the sides show the picture blurred (downscaled to 16x14, scaled up
linearly, dimmed). The window is high-DPI aware, so fullscreen renders at the display's
native resolution (e.g. 3840x2160). Frames are paced at 59.83 Hz by the frame timer. VSync
(on by default; `set_vsync`, `SDL_SetRenderVSync` 1, adaptive if that is refused) shows each
on the screen's refresh, so it never tears; the timer still sets the pace, so on a 60 Hz
screen about one frame in 350 is shown twice. Test runs turn it off to run uncapped.
`rondo.log` records the renderer and whether VSync is on.

Screen effects (`video.c`, `draw_effect`; Off by default): passes of the ordinary renderer,
no shaders. The picture is drawn at its size on screen into a render target, softened
sideways for Composite (four shifted copies blended in turn), drawn again added at a fraction
to make up for the darkening, and multiplied (`SDL_BLENDMODE_MOD`) by a scanline profile: a
1-pixel-wide texture with the brightness of every screen row, 1 - depth * cos^4 across each
game line, averaged over 8 points per row so lines come out even at any scale. The target
then goes on the screen, flat or for Curved CRT on a 48 x 36 mesh bowed outward (x scaled by
1 - k y^2, y by 1 - k x^2), under an aperture grille (a 3 x 1 RGB texture tiled at the
screen's own pixels, doubled from 1600 rows, multiplied), a glow (the picture downscaled to
128 x 112 and 64 x 56, added) and a vignette. Geometry takes its alpha from the vertices, not
the texture's alpha mod, so the mesh passes put it there. Each effect is set to keep the
picture's average brightness within about 6% of the plain picture; each costs under 0.4 ms
a frame at 1080p. Effect strength scales them by 0.6 / 1 / 1.4. The features test takes a
screenshot of each.

Cinematic skip: story scenes run in main state `$0A` (RUN does not skip them in the game).
Skipping runs the emulation at full speed, silently, until the state changes (the 3,566-frame
Stage 0 scene takes under a second), then records one rewind step across the whole scene.

The logo and the intro use the game's own skip instead (bank `$6B`, the overlay at `$8000`):
the logo (state `$00`) ends early on a new RUN press when `$3F83` and `$3F84` are both set,
with `$37 = $FF`, which sends state `$02` to sub-state `$03` (the title screen's script)
past the intro; the intro (state `$02` sub-state `$01`) goes to the title on a new RUN press
when `$3F83` is set. The game sets `$3F84` at the end of the logo and `$3F83` at the end of
the intro (and in the logo's first step when the backup RAM check at `$40E7` returns 0), so
on a first power-on START does nothing until both have been shown. Unless Skip cinematics is
Never, the frontend sets both flags during the logo and intro (`game_allow_power_on_skip`),
and Start, Jump or Attack (or Play on the start screen, or Automatically) makes it press RUN
for the game every 8 frames where it looks (`game_power_on_skippable`) until the title screen
is up: about 0.3 s from power-on. The title screen is silent either way; the game starts its
attract sequence about 14 s later.

Cheats (`game.c`): health losses are undone while playing (state `$05`); hearts are kept at
99 while playing, unless they drop more than 12 times a second (a tally), then left alone
until 3 quiet seconds pass or the state changes; lives losses are undone outside the menus.
Maria unlocked sets bit 0 of `$1F40` (the current save record) while playing; Play as Maria
sets the character byte `$9F` to 1 whenever a stage may be loading (outside gameplay and
while a stage sets up), so every stage loads Maria's code, the Prologue included.

Run (`game_apply_run`): Rondo sets the player's X velocity once when a walk starts (±$0140
for Richter, ±$0160 for Maria; Richter's jumps ±$0150). While the run button is held, those
exact values in the facing direction are scaled by 2.3 / 1.25 (SotN's run against its walk,
which equals Rondo's), and the walk animation's frame timer gets an extra step on 5 frames
of 6. The game's own movement code then handles walls, stairs and the camera.

The title screen's prompt (`prompt.c`): the game's "PUSH RUN BUTTON!" (six sprites in
palette 7 at Y 136, the same on both discs) reads "PUSH START BUTTON!" with a controller
and "PUSH ENTER KEY!" on the keyboard (`input_pad_last`: the kind of device pressed last; a
controller if one is connected and nothing has been pressed yet). Before each frame of state
`$02`, if the six sprites are in the sprite table, they are left out of that frame's picture
(`vdc_set_sprite_hide`, host side: they still count as drawn for the line limit and sprite
0's collision, so nothing the game can see changes); after it the new line is drawn into the
picture in the game's own letters, cut from those sprites' patterns in VRAM, with A, E, K
and Y drawn in the same style in `prompt.c`. Its colours come from the palette as it is, so
it fades with the title. No game graphics are kept in the source.

Start screen (`menu.c` page `PAGE_START`, the in-game menu's root swapped for one with Play
at the top; the option pages return to whichever root opened them): shown when rondo.exe
starts unless `--play` or the Start screen option is off. The game is loaded but does not
run behind it (no picture, no sound); Play starts it from power-on and goes straight to the
title screen with the game's own skip (unless Skip cinematics is Never), Load state loads
into it.

The look (`theme.c`; laid out after the Metroid: Other M port's menus, gothic, by candlelight
and moonlight, red kept to small rubies): panels are dark umber frames with a pointed-arch
top letting in pale moonlight, warmer towards the bottom, a gold border and inner line,
pinnacles at the arch's feet and a cross on its apex; dividers carry diamonds and a cross;
the selected row is a bar of candlelight with a gold cross for a cursor; notices are plaques
with pointed ends. The emblem is a rose window of blue and indigo glass lit by a candle
behind it. The start screen is a town at night: a deep blue sky, a pale moon high on the
left whose beams slant down onto the town, thin clouds and bats; a castle on a hill and the
town's rear rows in a cool mist; the town's warm glow; then the near row of houses (moonlit
roof edges, chimneys), a church with a lit belfry and street lanterns, the windows lit by
candles that flicker. Lights are added (`SDL_BLENDMODE_ADD`) as soft radial glows. The
title is beside the menu panel. Each page has a help line per item and
the buttons in the footer; panels are sized to their rows and open out when shown. All drawn
with SDL's renderer (`SDL_RenderGeometry`); text rasterised by stb_truetype (`stb_truetype.h`,
public domain) into glyph atlases per size, in fonts built into rondo.exe (`ui_fonts.c`,
generated by `tools/fonts/make_ui_fonts.py`; SIL OFL 1.1): Cinzel for menu text, Cinzel
Decorative for capitals, UnifrakturMaguntia (blackletter) for titles. Windows' fonts, then
SDL's debug font, stand in if one cannot be read.
Skip cinematics (START, or automatic) runs the story scenes (state `$0A`) fast; the logo and
the power-on intro (state `$02`, sub-states `$00`-`$01`: the narration and animated opening,
about 1:55 on both discs) use the game's own skip (above). Only the features test still runs
the intro fast, frame for frame, because its recorded input is tied to frame numbers.
START / F1 plays, Back does nothing there. The mouse works on every menu page
(`menu_item_at`, sharing the layout with `menu_draw`); the pointer is hidden while playing.

Test modes: `rondo.exe --autotest` (save, load, rewind), `rondo.exe --autotest-features
DIR` (plays the capture script with automatic skipping and all cheats, uncapped; writes
screenshots of the video modes, menu pages and start screen to DIR; checks the start
screen's keys and mouse layout; switches language at the end) and `rondo.exe
--autotest-start` (the start screen for 600 frames, checking the game waits behind it, a
mouse click on Play sent through the event queue, the title screen reached; then Jump
pressed during the intro skipping it, and Automatically from power-on, each by the game's
own skip with nothing run fast). All log to `rondo.log` and
keep their files in a `test` folder, never touching the player's saves. Their window
cannot take the keyboard focus, and they ignore real keyboard, mouse and controller input
(events and polled state alike): only the input events a test sends itself, marked with
the device id `TEST_INPUT`, are taken, so typing elsewhere while one runs cannot change it.

Showcase (`showcase.c`): `rondo.exe --showcase SCRIPT` plays a scripted tour in real time with
sound, for recording a video of the game (OBS capturing the window). The script presses and
lets go of keys at set frames of the window (`wait N`, `press KEY...`, `release KEY...`,
`tap KEY... [N]`, `mark TEXT`, `shot FILE`, `quit`; SDL key names). They reach the game as a
player's keys would: as `TEST_INPUT` events, and in place of SDL's keyboard state
(`input_use_keys`). So menus, macros, run, rewind and save states all work as for a player,
and real input is ignored. The window is 1920 x 1080 pixels and cannot take the focus. The
options the script changes are saved next to it (`SCRIPT.settings.ini`), not in the profile.
`SCRIPT.log` has the wall clock at frame 0 and each mark's frame and time, so captions can be
lined up with the recording. `--showcase-fast SCRIPT` runs it uncapped and silent, to check a
script with its shots. The game's own timing is the same either way, but the menus' animations
follow the real clock.

Profile: settings, saves, states and the remembered disc live in the pref folder
(`%APPDATA%\RondoRecomp\RondoRecomp`), or in the folder named by the `RONDORECOMP_PROFILE`
environment variable (`locate_profile_dir`), which Setup and rondo.exe started from each
other inherit: a whole separate player, e.g. to go through the first run again.
The build copies `SDL3.dll` and `libiconv-2.dll` next to the executable (on Linux
`libSDL3.so.0`, found through the programs' RUNPATH, `$ORIGIN`).

RetroAchievements (`achievements.c`, `http.c`; game 4855): RetroAchievements' client library,
rcheevos 12.5.0 (`third_party/rcheevos`, MIT; built with `RC_NO_THREADS` and only the CD hashing,
`tools/rcheevos_sources.cmake`), runs the achievements, leaderboards and rich presence.
- The disc is identified by RetroAchievements' PC Engine CD hash: MD5 of the 22-byte title at
  sector 1 + 106 of the first data track, then the boot program's sectors. The library's own
  code hashes it, reading through the runtime's disc reader (`Disc`, every image format the game
  takes). The English patch keeps the original's boot sector, so both discs hash to
  `dc5a0e432c9e8a9ab9f514b729b574f3` = game 4855.
- Memory as RetroAchievements maps a PC Engine CD:
  - `$000000` work RAM
  - `$002000` CD RAM
  - `$012000` Super System Card RAM
  - `$042000` backup RAM (2 KiB)

  These are `Pce.wram`, `cdram`, `superram` and `bram` in that order.
- The library is checked after every emulated frame, story scenes run fast included, but not
  while rewinding.
- Server requests run on a thread each, with WinHTTP on Windows and on Linux the system's
  libcurl, loaded at run time (`libcurl.so.4`, then the GnuTLS build). Their answers are
  handed to the library on the main thread (`http_poll`), so it needs no locking. The
  User-Agent is `RondoRecomp/<version> (<system>) rcheevos/<version>`.
- The account: a password login answers with a token, and only the token is kept
  (`settings.ini` `ra_user`, `ra_token`). Later starts log in with it, and a rejected token is
  dropped.
- Save states keep the achievements' progress (hit counts) in `slotN.state.ra` next to the
  state. A state without one resets them.
- Hardcore mode turns off state loading, rewind, the cheats and the run; the library asks for
  a restart when it is switched on (`RC_CLIENT_EVENT_RESET`).
- Whether hardcore counts is the server's call, by the User-Agent's first word. RondoRecomp is
  not a client it knows yet, so it puts a notice at the top of the set: an achievement of its
  own (id 101000001, 0 points, unlocking 5 s in, never sent back), "Warning: Unknown Emulator",
  "Hardcore unlocks cannot be earned using this emulator." It then records hardcore unlocks
  as softcore and keeps no leaderboard entries. The notice is shown as a RetroAchievements
  pop-up, not an unlock. When its text says hardcore cannot be earned, the library runs
  softcore for that game (so the counts and the unlocks are the server's), the pop-up and the
  menu say "softcore only", and hardcore's rules stay on as set (switching it on still
  restarts the game, `ach_take_reset`, as RetroAchievements requires). Each load asks again, so a
  client the server registers later gets hardcore with no change here.
- `rondo --test-achievements` hashes each installed disc, asks the server which game it is (no
  login needed), and exits 0 when both are game 4855.
- The features test registers an achievement of its own on the game's state (`$30` = 05, `$31`
  = 01) through the same memory map. It must fire at the first frame of play after the
  opening cinematic (16105), in that state.

### Headless runner

```sh
build/rondo_headless <game.cue> --frames 3000 --shot-every 150 --out work/shots \
    [--log-bios | --log-bios-all] [--press FRAME:run,i:LEN] [--profile] \
    [--watch BANK:ADDR] [--trace FRAME:COUNT] [--bios-reset syscard3.pce]
```

Investigation options: `--script` (the capture input script), `--ram 30,94,98` (print those
work-RAM bytes whenever one changes), `--poke ADDR=VAL` (write before every frame),
`--save-state FRAME:FILE` / `--load-state FILE` (start later runs mid-game), `--dump-ram
FRAME:FILE`, `--ram-trace FILE` (work RAM + pad after every frame, for offline searches),
`--cheats health,hearts,lives,maria,play-maria` and `--skip-cinematics` (the frontend's
`game.c`), `--run FRAME:LEN` (hold the run button), `--prompt pad|keys` (the title's
prompt as rondo.exe shows it), `--row-scroll A:B` (each frame's bands of rows by X scroll),
`--write-watch ADDR,...` (which
instruction changes those work-RAM bytes; interpreter), `--vram-watch LO:HI` (which
instructions write that VRAM range), `--dump-mem FRAME:FILE` (all 256 banks + MPRs, for
disassembly), `--dump-vram FRAME:FILE`, `--dump-adpcm FRAME:FILE` (the 64 KiB of ADPCM RAM), `--dump-sat FRAME` (sprite table), `--scroll-log FILE`
(scroll registers mid-screen per frame). Button
names for `--press` are lower case: `i`, `ii`, `select`, `run`, `up`, `down`, `left`, `right`.

The interpreter runs at about 2,600 frames per second (~43× real time).

Progress so far: boot, publisher logo, the full intro, attract mode, title, and the save-file
menu all render and run; menu input works. `--wav FILE` records the audio output.

### Hardware behaviour this depends on

- **VDC status flags are only latched when their interrupt is enabled.** Rondo's vblank
  handler checks the raster flag first and takes a raster-only path when it is set. If a raster
  match is latched while raster interrupts are disabled, it arrives together with vblank and the
  frame logic never runs again (the game froze on the logo before this was fixed).
- **The raster counter keeps counting below the picture, and the raster interrupt on the
  first line after it comes before vblank.** The counter is `$40` on the picture's first line
  and counts every line until the next picture starts, so a compare of `$40` + the picture's
  height matches the first line of vertical blank. Rondo's water areas (the Stage 1 ferry)
  use that: a raster split at the water line (69:47E2, effect 8 of the table at 69:44E9)
  saves sprite palette 0 (Richter's) and fills it with blue for his reflection, and sets
  RCR `$121` (picture height 225), whose interrupt restores it (69:477D). The handler reads
  the status once and handles one cause, so vblank (`vdc_vblank`, with the SATB DMA) is
  raised half a line later than the compare (`pce_run_frame`). Before this, compares stopped
  at the picture's end: the restore never ran, the next frame saved the blue palette, and

- Rondo never uses the timer: its timer handler is a bare `RTI`. The System Card leaves the
  timer stopped after reset (checked by running the original reset code with `--bios-reset`).
- Input arrives through the System Card's `EX_JOYSNS` variables (`$2228` held, `$222D` newly
  pressed, `$2232` previous), which the game refreshes every frame.
